# 📘 Module 2 — Data Link Layer

## 1. What is the Data Link Layer?

First, remember that the **OSI model** has 7 layers.

The **Data Link Layer is Layer 2**.

Its basic job is:

> **Move data safely between two devices that are directly connected.**

For example:

```text
Computer A  ───────────────  Computer B
              ↑
        Data Link Layer
```

The Data Link Layer takes data from the Network Layer and organizes it into something called a **frame**.

It has two important parts:

1. **DLC — Data Link Control**
2. **MAC — Medium Access Control** 

---

# 2. DLC — Data Link Control

DLC is mainly concerned with making communication **reliable and organized**.

It has three important jobs:

### A. Framing

Data coming from the Network Layer is divided into small units called **frames**.

Think about sending a letter.

You don't just send a piece of paper—you put it inside an **envelope**.

```text
Data → [ Envelope / Frame ] → Receiver
```

The envelope tells the receiver where one piece of information starts and ends.

Similarly:

```text
Data → Frame 1 → Frame 2 → Frame 3
```

Framing makes each frame distinguishable from the next one. 

---

### B. Flow Control

Imagine:

```text
Fast Sender  ─────────→  Slow Receiver
```

If the sender sends data too quickly, the receiver might not be able to process everything.

**Flow control** prevents this.

Simple definition:

> **Flow control controls how much data the sender can send before it needs to wait.** 

---

### C. Error Control

Data can be damaged or lost while traveling.

For example:

```text
Sender:   10110010
             ↓
           Network
             ↓
Receiver: 10100010
              ↑
          Error occurred
```

Error control detects problems and, depending on the protocol, allows the damaged/lost data to be sent again.

The PDF describes this using **ARQ — Automatic Repeat reQuest**.

> **ARQ means: if something goes wrong, request the data again.** 

---

# 3. MAC — Medium Access Control

Now imagine several computers sharing the same communication channel:

```text
       Computer A
            \
Computer B --- Shared Channel --- Computer C
            /
       Computer D
```

Who gets to use the channel?

That's the job of **MAC**.

MAC decides:

> **Which device can transmit and when?**

It also uses **MAC addresses** to identify devices on a local network. 

---

# 4. Framing

This is one of the important topics in the chapter.

The Data Link Layer needs to divide data into frames.

```text
Original data:

101010101010101010101010

          ↓

+--------+--------+--------+
| Frame1 | Frame2 | Frame3 |
+--------+--------+--------+
```

The receiver needs to know:

* Where does Frame 1 start?
* Where does it end?
* Where does Frame 2 start?

This is why **delimiters/flags** are used.

---

# 5. Byte Stuffing

Byte stuffing is used when special bytes appear inside the actual data.

The PDF describes it as adding an extra byte when a **flag or escape character** occurs in the data. 

Think of a special character:

```text
FLAG = F
ESC  = E
```

Suppose our data is:

```text
A B F C
```

The receiver might think `F` means:

> "The frame has ended!"

So the sender adds an escape character:

```text
A B E F C
```

The receiver performs **unstuffing** and gets:

```text
A B F C
```

### Remember:

**Byte stuffing = add an extra byte to protect special bytes in data.**

---

# 6. Bit Stuffing ⭐

Bit stuffing works with **bits instead of bytes**.

The PDF says that a `0` is inserted after five consecutive `1`s in the relevant flag-oriented data pattern so the receiver does not confuse data with the flag. 

For example:

```text
Original:

111111
```

After five `1`s, insert `0`:

```text
1111101
```

So:

```text
11111 → 111110
```

At the receiver, the extra `0` is removed.

This is called:

* **Stuffing** → sender adds the bit
* **Unstuffing** → receiver removes it

### Easy memory trick:

> **5 ones → put a 0**

---

# 7. Flow Control vs Error Control

This is very important for exams.

| Concept           | Main purpose                            |
| ----------------- | --------------------------------------- |
| **Flow Control**  | Prevent receiver from being overwhelmed |
| **Error Control** | Deal with damaged/lost data             |

Example:

### Flow problem

```text
Sender >>>>>>>>>>>>>>>>>>> Receiver
                  TOO FAST!
```

### Error problem

```text
Sender ─── Frame ───X───> Receiver
                  LOST
```

---

# 8. Noiseless Channel

A **noiseless channel** is an ideal channel.

We assume:

* Frames are not damaged.
* Frames are not lost.

The PDF introduces two protocols for this situation. 

## Protocol 1: Simplest Protocol

The sender continuously sends frames.

```text
Sender:

Frame 1 → Frame 2 → Frame 3 → Frame 4 → ...
```

It assumes:

> The receiver is always ready.

There is:

* ❌ No flow control
* ❌ No error control

Very simple, but not realistic.

---

# 9. Stop-and-Wait Protocol

This is easier to understand.

Instead of sending everything continuously:

```text
Frame 1
   ↓
WAIT
   ↓
Frame 2
   ↓
WAIT
   ↓
Frame 3
```

The sender:

1. Sends one frame.
2. Waits.
3. Gets an acknowledgment (**ACK**).
4. Sends the next frame.

The PDF describes exactly this behavior. 

### Example

```text
Sender                    Receiver

Frame 1  ---------------->

         <---------------- ACK

Frame 2  ---------------->

         <---------------- ACK

Frame 3  ---------------->

         <---------------- ACK
```

### Why use it?

Because a fast sender should not overwhelm a slow receiver.

---

# 10. Noisy Channel

Real communication isn't perfect.

A frame can be:

* Lost
* Damaged
* Duplicated

Therefore, we need **error control**. 

The main protocols are:

1. **Stop-and-Wait ARQ**
2. **Go-Back-N ARQ**
3. **Selective Repeat ARQ**

---

# 11. Stop-and-Wait ARQ ⭐

ARQ = **Automatic Repeat reQuest**

Example:

```text
Sender                    Receiver

Frame 1  ---------------->

         <---------------- ACK

Frame 2  --------X
              LOST

         [WAIT...]

Timeout!

Frame 2  ---------------->

         <---------------- ACK
```

The sender keeps a copy of the frame.

If the ACK doesn't arrive before the timer expires:

> **Send the frame again.**

The PDF specifically explains that Stop-and-Wait ARQ uses a timer and retransmits when the timer expires. 

---

# 12. Why Do We Need a Timer?

Imagine:

```text
Sender                    Receiver

Frame 0 ---------------->

          <-------------- ACK
```

Now suppose the ACK is lost:

```text
Frame 0 ---------------->

          <-------------- ACK
                         X LOST
```

The sender doesn't know what happened.

Did:

* the frame get lost?
* or did the ACK get lost?

So the sender waits for a certain amount of time.

That's the **timeout**.

Then it sends the frame again.

The PDF gives this exact situation as an example. 

---

# 13. Sliding Window Protocol ⭐⭐⭐

Stop-and-Wait is slow because:

```text
Send → Wait → Send → Wait → Send → Wait
```

We can make it faster.

Instead:

```text
Frame 1 → Frame 2 → Frame 3 → Frame 4
```

The sender can send **multiple frames before waiting for ACKs**.

The number of frames that can be sent at once is called the:

> **Window Size** 

For example, window size = 4:

```text
[ 1 ][ 2 ][ 3 ][ 4 ]  5  6  7
  ↑
Window
```

After acknowledgments arrive:

```text
  1   2   3   4   5   6   7
          [ 3 ][ 4 ][ 5 ][ 6 ]
```

The window **slides forward**.

That's why it is called **Sliding Window**.

---

# 14. Go-Back-N ARQ ⭐⭐⭐

Suppose we send:

```text
1 → 2 → 3 → 4 → 5
```

But Frame 3 is lost:

```text
1 ✓
2 ✓
3 ✗
4 ?
5 ?
```

In Go-Back-N, the receiver doesn't keep the later out-of-order frames.

The sender goes back and retransmits:

```text
3 → 4 → 5
```

So:

> **Go-Back-N = retransmit the missing frame AND everything after it.**

The PDF describes this behavior directly. 

### Memory trick:

**Go Back → Send Again from the problem.**

---

# 15. Selective Repeat ⭐⭐⭐

Selective Repeat is smarter.

Again:

```text
1 ✓
2 ✓
3 ✗
4 ✓
5 ✓
```

The receiver can keep Frames 4 and 5.

Only Frame 3 needs to be retransmitted:

```text
3 → 
```

So:

> **Selective Repeat = retransmit only the missing/damaged frame.**

The PDF notes that this improves bandwidth efficiency compared with Go-Back-N. 

---

# 16. Go-Back-N vs Selective Repeat

Remember this table:

|                                       | Go-Back-N           | Selective Repeat |
| ------------------------------------- | ------------------- | ---------------- |
| Lost Frame                            | Retransmit it       | Retransmit it    |
| Frames after lost frame               | Retransmit them too | Keep them        |
| Receiver buffers out-of-order frames? | ❌ No                | ✅ Yes            |
| Efficiency                            | Lower               | Higher           |
| Complexity                            | Simpler             | More complex     |

### Easy memory:

**GBN: "Go back and send everything again."**

**SR: "Send only the one that is missing."**

---

# 17. HDLC

**HDLC = High-Level Data Link Control**

It is a **bit-oriented data link protocol**.

It supports reliable communication and ARQ mechanisms. 

An HDLC frame contains fields such as:

```text
+------+---------+---------+----------+------+ 
| Flag | Address | Control |   Data   | FCS  |
+------+---------+---------+----------+------+
```

---

# 18. HDLC Frame Fields

### Flag

Marks the beginning and end of a frame.

The value is:

```text
01111110
```



---

### Address

Identifies the station involved in communication.

---

### Control ⭐

This is an important field.

It contains information about:

* Frame type
* Sequence numbers
* Acknowledgments
* Flow control
* Error control 

---

### Information

Contains actual data in applicable frames.

---

### FCS

**FCS = Frame Check Sequence**

It is used for error detection, using **CRC**.



---

# 19. HDLC Frame Types

There are three important types:

### I-frame

**Information frame**

Used mainly for carrying user data.

### S-frame

**Supervisory frame**

Used for things such as acknowledgments and flow/error control.

### U-frame

**Unnumbered frame**

Used for control/management operations.

---

# 20. Piggybacking ⭐

This sounds complicated, but it's actually simple.

Suppose A sends data to B:

```text
A ───── Data ─────> B
A <──── ACK ─────── B
```

That's two frames.

With piggybacking:

```text
A ───── Data ─────> B
A <── Data + ACK ── B
```

The ACK is attached to a data frame going in the opposite direction.

So:

> **Piggybacking = send ACK together with your own data.**

Benefits:

* Fewer frames
* Less overhead
* Better bandwidth utilization
* Higher efficiency 

---

# 21. Error Detection

Data can become corrupted during transmission.

There are two basic types discussed in the PDF.

## Single-bit error

Only **one bit** changes.

Example:

```text
Original: 101101
Received: 101001
             ↑
           changed
```



---

## Burst error

Two or more bits are affected.

```text
Original: 101101001
Received: 100011001
             ↑↑↑
          errors
```

The PDF defines a burst error as two or more changed bits. 

---

# 22. Redundancy

To detect or correct errors, we add **extra bits**.

These extra bits are called:

> **Redundant bits**

Think of them as additional information that helps the receiver check whether something went wrong. 

---

# 23. VRC / Parity Check ⭐

**VRC = Vertical Redundancy Check**

Also called:

> **Parity Check**

A **parity bit** is added to the data.

There are two types:

### Even parity

Total number of `1`s should be **even**.

Example:

```text
Data: 1011001
```

Count the 1s:

```text
1 0 1 1 0 0 1
↑   ↑ ↑     ↑
     = 4 ones
```

Already even, so parity bit can be:

```text
0
```

The PDF explains that even parity makes the total number of 1s even, while odd parity makes the total odd. 

---

# 24. LRC

**LRC = Longitudinal Redundancy Check**

It is also called:

> **2-D parity check**

Instead of checking just one data unit, the data is organized into **rows and columns**.

Think of:

```text
1 0 1 1
0 1 0 1
1 1 0 0
---------
Parity row
```

The receiver uses the redundant row to help detect errors.



However, LRC has limitations and can fail to detect certain patterns where errors occur in corresponding positions. 

---

# 25. CRC ⭐⭐⭐

**CRC = Cyclic Redundancy Check**

This is a very important error-detection technique.

It uses **binary/polynomial division**.

### Sender

```text
Original Data
     ↓
Generator
     ↓
Binary Division
     ↓
Remainder
     ↓
CRC
```

Then:

```text
Data + CRC
```

is transmitted.

### Receiver

The receiver divides again.

If:

```text
Remainder = 0000...
```

→ likely **no error detected**

If:

```text
Remainder ≠ 0000...
```

→ **error detected**



### Important term

The divisor used in CRC is called the:

> **Generator polynomial / Generator** 

---

# 26. Hamming Code

The PDF also introduces:

> **Hamming Code**

It is used for **error correction**. 

The important difference to remember is:

**Error detection:**

> "Something is wrong."

**Error correction:**

> "Something is wrong, and I can determine/correct the error."

---

# 27. ALOHA ⭐⭐⭐

Now we move to **Multiple Access Protocols**.

Imagine several people trying to speak using one microphone:

```text
Person A ─┐
Person B ─┼──→ One shared channel
Person C ─┘
```

If two people speak at the same time:

> **Collision!**

ALOHA is a MAC protocol for shared broadcast networks. 

There are two types:

1. **Pure ALOHA**
2. **Slotted ALOHA**

---

# 28. Pure ALOHA

Very simple rule:

> **If you have data, transmit immediately.**

Example:

```text
A → packet
B → packet
```

If they transmit at the same time:

```text
A ──┐
    ├── COLLISION
B ──┘
```

Then they wait a **random amount of time** and retransmit. 

### Pure ALOHA process

```text
Have data?
    ↓
Transmit
    ↓
ACK?
 ↙     ↘
YES     NO
 ↓       ↓
Done   Wait randomly
         ↓
      Retransmit
```



---

# 29. Slotted ALOHA

Slotted ALOHA improves Pure ALOHA.

Time is divided into equal **slots**.

```text
| Slot 1 | Slot 2 | Slot 3 | Slot 4 |
```

A device can transmit only at the **beginning of a slot**.

This reduces the chance of collision, but requires synchronization between devices. 

---

# 30. Pure ALOHA vs Slotted ALOHA ⭐

|                    | Pure ALOHA   | Slotted ALOHA     |
| ------------------ | ------------ | ----------------- |
| Transmission       | Anytime      | Beginning of slot |
| Synchronization    | Not required | Required          |
| Collisions         | More         | Fewer             |
| Maximum throughput | ~18.4%       | ~36.8%            |

The PDF gives the maximum throughput values as **0.184 for ALOHA** and **0.368 for Slotted ALOHA**. 

### Easy memory:

```text
Pure ALOHA       ≈ 18.4%
Slotted ALOHA    ≈ 36.8%
```

Slotted ALOHA is approximately **twice as efficient** at maximum throughput.

---

# 31. CSMA ⭐⭐⭐

**CSMA = Carrier Sense Multiple Access**

The key idea is:

> **Listen before you transmit.**

Imagine a person checking whether someone is already speaking before talking.

```text
Is channel busy?
       ↓
    YES → Wait
       ↓
     NO
       ↓
   Transmit
```

The PDF notes that CSMA improves throughput compared with ALOHA by listening to the channel before transmission. 

---

# 32. Types of CSMA

Your PDF discusses:

1. **Nonpersistent CSMA**
2. **1-persistent CSMA**
3. **p-persistent CSMA**

---

## Nonpersistent CSMA

If channel is idle:

```text
Transmit
```

If channel is busy:

```text
Wait random time
       ↓
Check again
```

Random waiting reduces collisions, but can waste some idle time. 

---

## 1-persistent CSMA

If channel is idle:

```text
Transmit immediately
```

If channel is busy:

```text
Keep listening
     ↓
Channel becomes free
     ↓
Transmit immediately
```

The problem is that if several devices are waiting, they may all transmit at the same time when the channel becomes free, causing a collision. 

---

## p-persistent CSMA

When the channel becomes free:

```text
Transmit with probability p
```

or

```text
Wait with probability (1-p)
```

It provides a tradeoff between the other approaches. 

---

# 33. CSMA/CD ⭐⭐⭐

**CSMA/CD = Carrier Sense Multiple Access with Collision Detection**

CSMA says:

> **Listen before transmitting.**

CSMA/CD additionally says:

> **Keep checking for a collision while transmitting.**

Process:

```text
1. Check channel
       ↓
2. Idle?
       ↓
3. Transmit
       ↓
4. Collision?
    ↙       ↘
  YES       NO
   ↓         ↓
 Stop      Done
   ↓
Wait random time
   ↓
Try again
```

The PDF gives these four basic steps.

## 🎯 One Very Easy Way to Understand the Entire Module

Think about sending packages:

**Framing** = Put each package in its own box.

**Flow control** = Don't send 100 boxes to a person who can handle only 10.

**Error control** = Check whether boxes arrived correctly.

**Stop-and-Wait** = Send one box, wait for confirmation.

**Go-Back-N** = If box #3 is missing, resend #3, #4, #5...

**Selective Repeat** = If box #3 is missing, resend only #3.

**Piggybacking** = Instead of sending a separate "I received it" message, include that confirmation when sending your own package.

**ALOHA** = Everyone can try to talk whenever they want → collisions can happen.

**CSMA** = Listen first, then talk.

**CSMA/CD** = Listen, talk, and stop if you detect a collision.

That is the core idea of the entire PDF.
